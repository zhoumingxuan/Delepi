# Delepi

Delepi（智能协作、准确交付）是一款基于 Electron + React + TypeScript 的 AI 桌面客户端，采用“主智能体 + 执行子智能体”双智能体协作架构，面向需要多步骤执行与准确交付的复杂任务。

## 1. 项目简介与双智能体架构

### 1.1 协作模式

Delepi 采用编排者—执行者模式，由两类智能体完成“理解—委派—执行—回传—再决策”的完整闭环：

- **主智能体（main-agent，编排者）**：理解用户需求并规划执行路径，通过 `delegate_executor` 工具将任务委派给执行子智能体；
  委派任务携带 8 个字段——任务名称、任务类型、任务目标、规则约束、交付物类型与描述、任务上下文、技能标签。
- **执行子智能体（executor-agent，执行者）**：接收委派任务，按绑定的技能模板调用工具完成执行。
- **任务结果与工作报告回传**：执行子智能体按最终输出协议回传执行状态、执行摘要、警告与错误清单及交付物文件，执行过程同步记录执行日志。
- **组长决策下一轮**：主智能体整合任务结果与报告，决定回复用户、继续委派下一轮任务或发起回归验证；同批次内互不耦合的任务并行执行。

上述协作可类比为“组长与组员”：组长负责理解需求、拆解派发任务、审阅工作报告并决定下一步；组员负责领取任务、调用工具执行并提交结果与报告。

这套分工还有个实打实的好处——省 token。组长派活时不带整段聊天记录：委派单上只有 8 个必要字段，连“任务上下文”也是从历史对话里提炼出的关键信息，不是全文搬运；
组员领到任务单就独立开工，不翻任何会话历史，干完只交回一份执行摘要；下一轮委派时，组长递过去的也只是上一个任务的名字和摘要。两边都不拖家带口，token 都花在任务本身上。
历史对话另有一道 64KB 阈值的压缩闸门（第 7 章细讲），越堆越长的历史到点就自动“瘦身”。

会话、消息、上下文压缩记录与应用设置通过本地 SQLite 持久化存储；会话中可上传文件（单次至多 10 个）作为任务输入。

### 1.2 内置技能模板

skills/ 目录内置 8 个技能模板，每个模板对应一个技能标签：

| 技能 | 适用范围 |
| --- | --- |
| 问题诊断 | 报错、异常、差异、瓶颈等问题追踪与根因定位 |
| 方案设计 | 方案、结构、接口、流程、数据与执行路径设计 |
| 自动化交互 | 浏览器、远程、界面等真实交互与截图识别取证 |
| 用例编写 | 按需求与验收口径设计可执行测试用例 |
| 用例执行 | 按既有用例执行网站、API、单元与应用测试 |
| 执行变更 | 新增、修改、修复、重构、优化等产物变更闭环 |
| 调查研究 | 建立证据链，判断对象间事实关系与结论成立性 |
| 视觉设计 | 海报、封面、插画、图标、示意图等视觉产出 |

主智能体委派任务时绑定技能标签（每个任务 1 到 3 个），执行子智能体就按对应模板的流程干活，一套模板就是一套现成的工作方法。

每个模板说白了就是 skills/ 目录下的一份 Markdown“工作说明书”——想给 Delepi 加一门新手艺，照着现成模板写一份新的 md 文件、在常量里登记一个技能标签、再接上少量注册代码就够了，
执行循环、工具层这些核心架构一行都不用动。扩展一门技能的成本，大致就是“写一份说明书”的成本。

## 2. 开发环境准备

### 2.1 开发环境要求

- Node.js 与 npm（建议使用 LTS 版本）；
- 首次安装依赖、启动应用与打包需要网络（下载 npm 依赖、Electron 二进制与内置 Python 组件）。

### 2.2 快速开始

```bash
# 安装依赖
npm install
# 若环境变量 NODE_ENV=production 导致 devDependencies 被跳过，请改用：
# npm install --include=dev

# 启动应用
npm run dev
```

首次启动时，应用会自动下载并初始化内置 Python 3.14.6 环境；在应用内“设置 → 模型”中完成大模型 API 配置（见第 3 节）后即可开始使用。
会话数据保存于本地 data/ 目录（已被 .gitignore 忽略，不会随版本提交）。

不止会话数据——上传的文件、任务执行过程记录、最终交付物，全部落在你本机的目录里，Delepi 不设任何云端服务端；
应用对外的网络通信只有三件事：调用你自己配置的大模型 API、首次启动下载内置 Python、任务执行中按需安装依赖。
只要 API 服务本身是官方安全的，你的会话记录和个人信息就不会经 Delepi 外泄——数据都存在你自己的电脑上。

## 3. 大模型 API 配置

所有模型配置在应用内“设置 → 模型”页完成，保存后写入本地 SQLite 数据库。

### 3.1 必填项与模型分组

Delepi 通过 OpenAI 兼容 API 对接大模型服务，模型配置分为三组：

| 模型分组 | 配置项 | 要求 |
| --- | --- | --- |
| 主智能体模型 | Base URL / API Key / 模型名称 | 必填（配置就绪检查仅校验本组三项与 Python 环境） |
| 执行子智能体模型 | Base URL / API Key / 模型名称 | 用于委派任务执行，需单独配置 |
| 视觉模型 | Base URL / API Key / 模型名称 | 仅图片分析场景需要（见 3.2） |

注意：API Key 以明文存储在本地数据库中（不出你的电脑），请勿在共享或公开环境中泄露。

### 3.2 图片分析配置（多模态 + 视觉识别双开）

需要让模型理解上传图片、或使用图片识别工具分析本地图片时，须同时满足以下三项：

1. 开启“支持多模态协议”（主智能体多模态，默认开启）；
2. 开启“启用视觉识别”总开关（默认开启）；
3. 填写视觉模型 Base URL / API Key / 模型名称（图片识别工具在运行时直读该组配置）。

不进行图片分析时，无需配置视觉模型。
视觉 / 多模态模型示例（仅为示例列举，不构成支持范围清单）：Qwen3.5～Qwen3.8 系列、Kimi K3、MiniMax M3 等。

### 3.3 视觉识别开关联动说明

- 视觉识别默认开启。开启时会提示“开启视觉识别需配置模型 API，否则图片识别会报错”；视觉模型三项未配置时，开关旁同步显示未配置警示。
- 关闭视觉识别后：
  - 视觉模型三个输入框（Base URL / API Key / 模型名称）禁用，已填写的值保留；
  - “支持多模态协议”开关同步禁用并提示暂不生效——多模态实际生效条件为“视觉识别开启且多模态协议开启”，即关闭视觉识别后多模态能力随之关闭；
  - 图片识别工具双层禁用（工具声明层移除 + 执行层拦截），委派任务无法再调用该工具。

### 3.4 思考程度

执行子智能体提供三档思考程度：低（更快响应）、高（均衡推理）、最大（深度推理）。默认档位为“最大”。

## 4. 能做什么：应用场景与优势

先讲清楚这套东西最核心的一点：你不需要懂任何配置。
你把需求说清楚——“帮我看看这个报错是怎么回事”“把这份合同的条款梳理一下”“给这组财报数据核对一遍再画张趋势图”——主智能体会自动判断该做什么（自动选任务类型）、该用什么方法（自动配技能标签），
然后通过委派工具把任务交给执行子智能体，一步步执行、一轮轮闭环，直到把你的需求办完。整个过程你只管提需求、看结果，不用手动配任务、配技能、配类型。

为什么能做到“全自动”？因为主智能体不是靠猜：它要委派任务，就必须把任务名称、任务类型、任务目标、规则约束、交付物类型、交付物描述、任务上下文、技能标签这 8 个字段全部填清楚（缺一不可）；
选任务类型要符合内置触发规则；配技能要按技能标签对应的工作流模板来。所以下面两节，就是这套“自动判断”背后的两本字典：任务类型管“做什么”，技能标签管“怎么做”。

### 4.1 任务类型：做什么

任务类型一共有 8 种，主智能体根据你的需求自动选择，每种都有明确的触发规则和交付类型限制：

- **信息整理**：材料比较杂、事实比较散时，先把关键特征、结论和证据链汇总核实，交付**权威结论**。
- **诊断问题**：遇到报错、异常、差异、瓶颈、错误结果、状态不一致这类问题，分析实际根因，交付**权威结论**。
- **研究探索**：需要交叉分析、深挖显式/隐式/细微线索时使用，交付**线索集合**或**关键材料**。
- **设计方案**：目标对象还缺核心设计、没法直接落地时使用，交付**方案**。
- **统筹规划**：后续任务复杂度高、需要先明确整体规划时使用，交付**详细规划**。
- **执行落地**：事实和结论都齐了、要真正动手产出东西时使用，交付类型按实际产物确定（改好的文件、生成的图表、写完的文档都算）。
- **编写用例**：需求里包含“写测试用例”，或者最终交付物缺验证手段时使用，交付**测试用例**或**文件链接**。
- **验收验证**：需要执行测试用例、对最终交付物做回归验证时使用，交付**权威结论**。

可以这样理解：任务类型就是“这一轮要干的事”，复杂的需求会被自动拆成多轮任务，按触发规则一件件委派，直到目标达成。

### 4.2 技能标签：怎么做

任务类型决定“做什么”，技能标签决定“怎么做”。技能标签一共 8 种，每一种都对应 skills 目录下的一套专业工作流模板——选了这个技能，执行子智能体就会按这套模板一步步走，而不是自由发挥：

- **问题诊断**（issue-location）：报错、异常、差异、瓶颈、错误结果、状态不一致等问题追踪和根因定位。
- **方案设计**（solution-design）：方案、结构、接口、流程、数据、权限、交互和执行路径设计。
- **自动化交互**（simulation-operation）：在授权范围内执行真实请求、浏览器、远程命令、界面交互、文件链路或截图识别，并取得可核验证据。
- **用例编写**（use-case-writing）：按需求、变更、接口、流程、风险或验收口径设计可执行测试用例。
- **用例执行**（use-case-execution）：按既有测试用例执行网站、API、单元和应用程序测试，记录执行过程、阻塞和结果。
- **执行变更**（change-execution）：新增、修改、修复、重构、优化等会改变既有或新增产物的任务。
- **调查研究**（research-analysis）：基于已知或可取得材料建立证据链，判断研究对象之间的事实关系、比较关系和结论成立性。
- **视觉设计**（visual-design）：海报、封面、插画、图标、示意图、视觉素材等视觉内容的设计和生成。

技能标签由主智能体自动绑定，一个任务绑定 1 到 3 个技能，多了反而不聚焦。原则上任何任务类型都可以使用任何技能标签，但有两条内置限制值得知道：
任务类型为【研究探索】时禁止使用【问题诊断】技能——探索阶段不该被诊断思路框死；任务类型为【诊断问题】时必须使用【问题诊断】技能——专业的问题对专业的方法。
这两条限制写死在提示词里，保证“做什么”和“怎么做”始终匹配。

### 4.3 典型应用场景

下面用几个具体场景，把“智能体自动怎么干”和“相比传统方式优势在哪”讲透。

**软件开发场景**

- **改 BUG**：把报错信息、日志、复现步骤丢给它（也可以附带截图）。
  - 主智能体先触发【信息整理】汇总关键事实 → 再触发【诊断问题】并绑定【问题诊断】技能定位根因 → 确认后触发【执行落地】绑定【执行变更】技能实施修复。
  - 需要回归时，追加【编写用例】（绑定【用例编写】技能）和【验收验证】（绑定【用例执行】技能）做完整闭环。
  - 传统做法是人先读日志猜原因、再手改代码、再手写回归用例，每一步都要人盯着；这里全程由主智能体编排，你只需要在关键节点确认方向。
- **做项目**：描述项目目标、约束与现有材料。
  - 【信息整理】收集核实事实 →【设计方案】绑定【方案设计】技能产出核心方案 →【统筹规划】产出详细执行规划 →【执行落地】按规划实施。
  - 传统做法要自己梳理需求、画方案、排计划、盯执行；这里方案和规划由专业模板保证质量，你只负责说清楚要什么。
- **自动化测试**：提供需求、变更说明或被测对象。
  - 【编写用例】绑定【用例编写】技能生成可执行测试用例 →【验收验证】绑定【用例执行】技能逐条执行并输出执行报告与缺陷清单。
  - 涉及真实界面交互与截图取证时，由【自动化交互】技能在 Python 运行时安装并使用浏览器自动化库，按用例驱动页面操作，以截图与识别结果核验界面状态。
  - 相比手工点点点，这套流程把“写用例—跑用例—取证”串成了自动闭环。

**法律与合规场景**

- **合同条款梳理与风险审查**：把合同文档（Word/PDF）作为资料文件提供。
  - 【信息整理】提取条款与关键事实 →【诊断问题】定位风险点（比如违约责任、争议解决、保密义务等条款的缺失或表述不清）→【设计方案】给出修改方案 →【执行落地】产出修改版本文档 →【验收验证】输出审查报告。
  - 要说明的是：这套能力基于内置 Python 的 Word/PDF 读写与文本处理能力，处理的是你提供的资料文件本身，不会自动联网检索外部法律数据库。
  - 它的价值在于——条款梳理、风险点定位、修改建议、审查报告都按专业工作流模板产出，每一步有据可查，不会漏项。

**财务报表场景**

- **读财报、核对数据、生成图表**：上传财报 PDF 或 Excel 文件。
  - 【信息整理】梳理关键财务数据 →【执行落地】用内置 Python 的 openpyxl / pandas / pdfplumber 读取并核对数据，
    用 matplotlib 生成趋势图、占比图等图表 →【验收验证】核对数据与图表的准确性后交付。
  - 相比手动开 Excel 逐格核对、再手工画图，这里从“读文件—核数据—出图表—验结果”整条链路自动完成，图表和数字都经过校验，不容易出现“数据抄错、图表对不上”这类问题。

**研究分析场景**

- **资料整理 → 线索深挖 → 交叉验证 → 结论报告**：把研究资料（文档、报表、数据文件）交给它。
  - 【信息整理】汇总事实与证据 →【研究探索】绑定【调查研究】技能，基于材料建立证据链、交叉验证各对象之间的事实关系 → 再委派【信息整理】把线索提炼成结论 → 输出结论报告。
  - 相比自己翻资料、做笔记、反复核对，这套流程把“整理—深挖—验证—成文”按模板串起来，线索不丢、结论有依据。

### 4.4 为什么适合这些场景

回头看这些场景，它们有几个共同点：目标明确（改好 BUG、出份审查报告、核对完数据）、材料可提供（日志、合同文件、财报、研究资料）、产出可验证（修复结果、报告、图表都能被检查）。这恰好是 Delepi 最擅长的地方：

- **自动委派，不用人盯流程**：主智能体按触发规则自动决定先做什么、后做什么，每一轮委派完自动判断下一步，你不需要在中间当“监工”。
- **自动配置，不用人配参数**：任务类型、技能标签、交付类型全部自动选择，你永远不需要手动去配“这个任务该用哪个类型、绑哪个技能”。
- **多轮闭环，边做边验**：复杂需求拆成多轮任务，每轮结果回到主智能体继续推进，过程中随时可验证、可调整。
- **验收兜底，保证准确交付**：重要交付物都会走【编写用例】+【验收验证】闭环，交付前先被用例检验过，避免“看起来做完了、实际经不起检查”。

一句话总结：这套机制把“判断、分工、执行、验证”都自动化了，你要做的就是描述清楚需求，然后验收结果。

## 5. 执行能力与工具

上一章讲了“派活”的逻辑，这一章说说“干活”的家伙什——执行子智能体真正动手时，靠的是三把工具和一套内置 Python 环境。

**三大执行工具**

- **run_exe（命令行执行）**：执行非交互、多行脚本，适合跑命令、批处理这类操作。单段脚本不超过 8000 字符，默认 180 秒超时，输出超限自动截断，统一按 UTF-8 处理，
  并且会拒绝挂起、常驻类风险命令——既给足了能力，也防住了“卡死”。
- **run_with_python（Python 脚本执行）**：写 Python 代码执行。脚本会先落盘、经过 py_compile 预校验通过后才真正执行，默认 180 秒超时，同样统一 UTF-8，
  适合复杂逻辑、批处理、文件改写这类活。
- **inspect_image（图片识别）**：识别本地图片中的可见事实——文字、数字、界面元素、表格结构、异常细节等。它运行时直读视觉模型配置，需要“视觉识别开启”（视觉识别总开关与主模型多模态双开）才可用；
  不做图片分析时，不需要配置视觉模型，工具会自动降级为前两个。

**内置 Python 环境**

执行子智能体自带一套 Python 3.14.6 环境（首次启动自动下载初始化），并预置 14 个第三方包，覆盖能力相当广：

- 文档读写：Word（python-docx）、Excel（openpyxl、xlsxwriter）、PPT（python-pptx）、PDF（pdfplumber、PyPDF2）；
- 网络与远程：HTTP 请求（requests、httpx）、SSH 连接（paramiko）；
- 图像处理：pillow；
- 数据与可视化：pandas、numpy、matplotlib、networkx（数据报表、图表、组织架构图绘制）；
- TCP / UDP 通信由 Python 标准库 socket 支持。

依赖安装级别可选：核心 6 包 / 推荐 14 包（默认）/ 完整 24 包，支持配置 pip 镜像源。预置清单之外的依赖（比如浏览器自动化库）可以在任务执行过程中联网安装，装完即可使用。

把这一章和上一章的场景对照起来看就很清楚：处理法律文档靠 python-docx / pdfplumber 读 Word 和 PDF；核对财务报表靠 openpyxl / pandas 读写 Excel、matplotlib 画图；
做研究分析靠文档解析、数据整理加图表输出；自动化测试靠浏览器自动化扩展加截图识别。
工具是“手”，技能模板是“流程”，两套配合，前面说的那些场景才真正落地。

## 6. 技术特性

Delepi 能“自动判断、多步执行、准确交付”，不是靠模型“自觉”，而是靠一整套实打实的技术特性：全中文提示词、Mermaid 流程图、注意力锚点与图钉特性、任务类型标签、技能标签、
委派字段全必填、技能限制规则、双智能体分工。本章逐条用大白话讲清每个特性是什么、为什么这么设计、好处在哪里。

### 6.1 全中文提示词：中文一个 token 就能说准意思

Delepi 的系统提示词、技能模板、工具描述、触发规则、输出协议，整条链路全部用中文写。这套设计看中的是中文的表意效率：**中文一个 token 往往就能表达一个准确的意思，英文常常要拼好几个 token，甚至还要考虑语态**。

举两个例子就明白了：

- 【诊断问题】四个字就是一个完整、准确的标签；换成英文得写 “diagnose the problem”，用好几个词不说，还得纠结用 diagnose、diagnosing 还是 diagnosis，词形一变、时态一变，意思就可能跟着偏。
- 【线索清单】四个字搞定一件事；英文 “list of clues” 是一串词，拆开每个词都有别的意思，拼在一起才是想要的那个。

好处很直白：**标签短、意思准**。全中文体系里，一个标签对应一个概念，模型读到标签就能直接对上概念，整套提示词里“什么词就是什么意思”，不存在第二种理解。

### 6.2 Mermaid 流程图：把做法画成固定路线，正好对上大模型的模式学习

主智能体的提示词里内嵌了一张完整的 Mermaid 标准流程图，从 START 节点到 END 节点，每个节点干什么、往哪走，全部画死。

看中的是流程图的**结构化**：把“处理逻辑”变成固定的“节点 + 箭头”，先做什么、后做什么、什么条件下走哪条分支，清清楚楚摆在那里。
而大模型本质上是做**模式学习**的——给它一个固定的结构模式，它就顺着这个模式走。Mermaid 流程图正好适配这种学习方式：节点是模式、链路是模式、分支判断也是模式，模型照着结构走，不会每一步自己发明路线。

打个比方：没有流程图，模型像在陌生城市里凭感觉开车，每个路口都能随便拐；有了流程图，等于给它一张导航地图，走哪条路、在哪个路口转弯都是定好的，只能沿着路线开。流程图还明确要求节点不得跳过、不得重排、不得合并，路线的完整性有硬约束。

### 6.3 注意力锚点与图钉特性：先钉住路线，再盯住细节

这一节讲两个容易被看漏的设计：注意力锚点和图钉特性。

**注意力锚点**：Delepi 的提示词写得非常“标签化”——关键概念全部用【】方头括号括起来，像【诊断问题】【研究探索】【事实、结论、线索】【流程节点链路】。
更关键的是输出侧的要求：技能模板里逐字写着“必须记录并输出按【执行变更流程图】实际执行的【流程节点链路】”，也就是要求把流程图上的重点标签完整写出来，而不是笼统说一句“按流程执行了”。

为什么这招管用？大模型内部有很多层注意力计算，生成内容时注意力会在多层之间不断分配。提示词里反复出现的【】标签，加上“完整写出流程节点链路”的输出要求，等于在每一层都打下了锚点——
**注意力被不断收拢到流程图上**，模型一路被拽着沿流程图走，不容易跑偏。就像开车时导航一直在念“前方路口直行”，你的注意力始终锚在路线上，想跑神都难。

**图钉特性**：提示词里大量出现【显式】【隐式】【细微】【极难发现】这四种标记，而且它们大多数时候并不要求单独输出，作用是**做重点标记**——提醒模型：显眼的要看，藏着的要看，细微的要看，极难发现的更要看。

这背后的逻辑是：**当你努力去发现细小粒度的东西时，大粒度的东西自然也逃不掉**。先难后易、抓小放大——连针尖大的问题都找得出来，还怕看不见明显的吗？反过来，只盯着大粒度的东西，细节就会从眼皮底下溜走。

### 6.4 任务类型：先定下标签，后面不走偏

主智能体委派任务前，必须先从 8 个任务类型里选定一个：信息整理、诊断问题、研究探索、设计方案、统筹规划、执行落地、验收验证、编写用例。这个设计有两个功能：

1. **约束后续生成不走偏**。大模型是自回归的——一段一段往后生成，先生成出来的内容会带着后面的内容走。先让模型定下任务类型标签，等于先把“这是件什么事”钉死，
   后面生成的内容就被这个标签约束住，走着走着跑偏的概率大大降低。
2. **避免任务糅杂在一块**。规定任务类型，就是规定“这次委派只干这一类事”。不同类型的活不搅在一起干，就不会形成那种“又要整理、又要诊断、又要设计”的粗粒度大杂烩任务——任务边界清楚，执行才聚焦。

### 6.5 技能标签：限 1~3 个，任务不糅杂

任务类型定了“做什么”，技能标签定“怎么做”。主智能体从 8 个技能标签（问题诊断、方案设计、自动化交互、用例编写、用例执行、执行变更、调查研究、视觉设计）里为任务绑定技能，
且数量被硬性限制在 1~3 个（skills 数组 minItems=1、maxItems=3）。

道理与 6.4 的第二个功能一样：**标签定得少，任务才聚焦**。如果允许一次绑一大堆技能，等于让一次任务同时按很多套方法干，任务的粒度跟着变大、内容跟着糅杂。
通过“设定技能标签 + 限制标签数量”这两下，每次委派就被限定在 1~3 套方法能干完的范围内——任务不糅杂，粒度粗不了。

### 6.6 委派 8 字段全必填：委派前被迫把任务想清楚

主智能体委派任务只用 delegate_executor 一个工具，它的 8 个字段——taskname（任务名）、tasktype（任务类型）、tasktarget（任务目标）、constraints（约束）、
deliverytype（交付类型）、deliveryspec（交付规格）、context（背景上下文）、skills（技能标签）——**全部必填**，缺一个调用直接被拒绝。

这个设计的作用是：**逼着主智能体在委派之前把任务想清楚**。任务叫什么、什么类型、目标是什么、有什么约束、交付什么、怎么交付、背景是什么、用什么方法——一项一项填全了，才允许发出去。
与其让模型自由发挥一大段话，不如让它填一张必须填满的表；表填满了，任务定义自然完整，同样是靠结构化手段约束生成、不让它跑偏。

### 6.7 两条技能限制规则：防止技能跟任务错配

原则上，任何任务类型都可以搭配任何技能标签，但有两条硬限制：

- 任务类型为【研究探索】时，禁止使用【问题诊断】技能——探索阶段不该被诊断思路框死；
- 任务类型为【诊断问题】时，必须使用【问题诊断】技能——专业的问题对专业的方法。

两条规则防的是同一件事：**技能与任务错配**。任务和方法对不上号，轻则白费功夫，重则跑偏方向。这两条限制同样写死在提示词里，“做什么”和“怎么做”始终对得上号。

### 6.8 双智能体分工：一个管规划，一个管执行

Delepi 用两套提示词分别驱动两个智能体：主智能体只做理解、拆解、规划、委派；执行子智能体只管按模板执行、调用工具、产出可核验的结果。

**规划与执行分离**带来的好处：主智能体的上下文里不掺执行细节，执行子智能体的上下文里不掺全局规划，两边互不污染、各自专注。
想的人专心想，干的人专心干，谁也不用一边规划一边执行来回切换。

顺带还有一笔“轻装账”：执行子智能体每次开工只带两条消息——一条系统提示词、一条任务说明（8 字段任务卡、提炼过的任务上下文、上一任务的摘要、技能模板），
不带任何会话历史，干完交回结果就走；主智能体拿到的也只是执行摘要和交付物，不是整段执行过程。两头都干净，token 也就都省在了刀刃上。

小结：这一章的技术特性说到底是同一件事——用固定的结构（中文标签、流程图、锚点、字段、规则、分工）让模型照着走。结构稳了，模型的输出才稳。

## 7. 上下文压缩能力

对话越聊越长，历史消息越堆越多，模型能“记”住的东西是有限的。Delepi 的上下文压缩，就是把历史对话整理成一份高质量的“记忆”：
当历史消息超过 64KB，或开启多模态后当前输入带图片时，自动触发一次压缩，旧的历史消息整体换成一份六章节的“背景信息”，主智能体带着这份精简记忆继续干活——
这也是第 1 章说的省 token 的另一半机制：长对话不会把历史原样越拖越长，而是到点就归档瘦身。
它的技术特点有三条主线：**只保留事实、结论、线索、特征，从源头减少幻觉；按时间先后规整排序；归纳成六个章节的结构化归档**。

### 7.1 只保留事实、结论、线索、特征：从源头减少幻觉

压缩时，Delepi 会对近期的用户输入和助手回复做特征全量提取，但写进总结里的东西有严格限定：**只保留事实、结论、线索、特征四类**。

为什么这么限制？因为总结一旦写进臆测和猜测，后续对话就会把它当成“历史事实”反复引用——臆测进了记忆，幻觉就有了土壤。
反过来，只保留事实、结论、线索、特征，总结里不带臆测，等于**从源头减少幻觉**：记忆干净，后面照着记忆干活才不容易编。

压缩指令里的几个实测细节，都是为“记忆干净”服务的：

- **原样保留**：指令逐字要求“必须严格的按照时间顺序原样保留”用户提供的事实信息和所有已确认的【事实、结论、线索】——对这部分内容只搬运、不改写。
  让模型“概括”事实等于让它转述，转述就可能走样；原话照抄，记忆才可信。
- **分档限量**：特征与对话按“全部或者最近10轮对话”的口径保留，用户意图按“全部或者最近10条用户表达的意图”的口径保留——既控制规模，又保证最新的内容不丢。
- **防自引用污染**：指令明确“绝对不要把这次生成总结的请求写进总结”。如果模型把“用户要求总结历史”也当成谈话内容写进去，下次压缩又会把“关于总结的总结”再总结一遍，
  记忆里全是总结请求的影子，真正的对话内容反被挤掉。这条禁令把污染源直接掐掉。

### 7.2 时序性：把历史对话按先后顺序规整排好

压缩明确要求体现时序：指令逐字写着“必须严格的按照时间顺序原样保留”“务必体现对话的用户意图和具体时序”；六个章节里有三个章节的标题直接要求“（同时说明具体时序）”。

为什么时序这么重要？因为对话是有先来后到的：用户的意图是怎么一步步变的、约束是什么时候改的、线索是什么时候冒出来的——这些先后关系一旦乱了，模型就可能把早期结论当成最新结论、把旧约束当成现行约束，记忆就成了糊涂账。

所以压缩相当于**把历史对话按时间重新排队、规整排序**：先来后到一目了然。承接历史时，系统还会说明“【消息序号】越小表示消息越早”，让模型能把压缩记忆和当前输入对上时间线，谁先谁后不会错位。

### 7.3 六个章节的结构化：像档案柜分格归档

压缩总结最终被归纳成六个互相不耦合的章节，名称与源码逐字一致：

1. 事实和结论清单
2. 线索清单
3. 用户输入信息中特征清单（同时说明具体时序）
4. 用户历史意图（同时说明具体时序）
5. 历史对话概要（同时说明具体时序）
6. 通用执行任务参考经验

这是**结构化**的直接体现：像档案柜分格归档，每格只放一类东西。事实放事实的格子，线索放线索的格子，模型以后要回忆什么，直接去对应章节找就行，不用在整段历史里从头翻到尾；六个章节互不耦合，看事实清单时不会被线索清单“串台”。

第六格“通用执行任务参考经验”也有讲究：它依据上下文分析出的所有事实和所有【显式/隐式/细微/极难发现】的特征，总结出可供后续任务参考的通用经验；没有就写无；并且注明后续执行环境可能变化，经验仅供参考。

三条主线合起来就是：**提炼（只留四类信息）、排序（时序规整）、归档（六章节结构化）**。历史再长，记忆也是干净、有序、好查的。

## 8. 适配与不适配场景

Delepi 以“准确度优先”为性能取向，对应代价是流程较长：

- **适配场景（准确度优先的多步复杂任务）**：缺陷修复与根因诊断、项目方案与统筹规划、自动化测试与网页自动化、文档批量处理等。此类任务通过多轮委派、强制输出约束与验收闭环换取更高的完成准确度。
- **主要代价**：需求理解、任务委派、工具执行、结果回传与再决策构成多轮循环，整体耗时高于单轮直答，不追求极致响应速度。
- **不适配场景**：追求秒级即时响应的轻量问答、简单单步查询或单条文本改写等任务；此类任务的流程开销大于收益，建议直接使用普通对话工具。
