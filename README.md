# Delepi

Delepi（智能协作、准确交付）是一款基于 Electron + React + TypeScript 的 AI 桌面客户端，采用「主智能体 + 执行子智能体」双智能体协作架构，面向需要多步骤执行与准确交付的复杂任务。

## 1. 项目简介与双智能体架构

### 1.1 协作模式

Delepi 采用编排者—执行者模式，由两类智能体完成「理解—委派—执行—回传—再决策」的完整闭环：

- **主智能体（main-agent，编排者）**：理解用户需求并规划执行路径，通过 `delegate_executor` 工具将任务委派给执行子智能体；委派任务携带任务名称、任务类型、任务目标、规则约束、交付物类型与描述、任务上下文和技能标签。
- **执行子智能体（executor-agent，执行者）**：接收委派任务，按绑定的技能模板调用工具完成执行。
- **任务结果与工作报告回传**：执行子智能体按最终输出协议回传执行状态、执行摘要、警告与错误清单及交付物文件，执行过程同步记录执行日志。
- **组长决策下一轮**：主智能体整合任务结果与报告，决定回复用户、继续委派下一轮任务或发起回归验证；同批次内互不耦合的任务并行执行。

上述协作可类比为「组长与组员」：组长负责理解需求、拆解派发任务、审阅工作报告并决定下一步；组员负责领取任务、调用工具执行并提交结果与报告。

会话、消息、上下文压缩记录与应用设置通过本地 SQLite 持久化存储；会话中可上传文件（单次至多 10 个）作为任务输入。

### 1.2 内置技能模板

skills/ 目录内置 9 类技能模板：

| 技能 | 适用范围 |
| --- | --- |
| 调查研究 | 建立证据链，判断对象间事实关系与结论成立性 |
| 问题诊断 | 报错、异常、差异、瓶颈等问题追踪与根因定位 |
| 方案设计 | 方案、结构、接口、流程、数据与执行路径设计 |
| 执行变更 | 新增、修改、修复、重构、优化等产物变更闭环 |
| 自动化交互 | 浏览器、远程、界面等真实交互与截图识别取证 |
| 用例编写 | 按需求与验收口径设计可执行测试用例 |
| 用例执行 | 按既有用例执行网站、API、单元与应用测试 |
| 视觉设计 | 海报、封面、插画、图标、示意图等视觉产出 |

其中 8 类已纳入任务技能标签，可由主智能体在委派任务时绑定（每个任务至多 3 个）。

## 2. 开发环境准备

### 2.1 开发环境要求

- Node.js 与 npm（建议使用 LTS 版本）；
- 首次安装依赖、启动应用与打包需要网络（下载 npm 依赖、Electron 二进制与内置 Python 组件）。

### 2.2 快速开始

```bash
# 安装依赖
npm install
# 若环境变量 NODE_ENV=production 导致 devDependencies 被跳过，请改用：
# npm install --include=dev

# 启动应用
npm run dev
```

首次启动时，应用会自动下载并初始化内置 Python 3.14.6 环境；在应用内「设置 → 模型」中完成大模型 API 配置（见第 3 节）后即可开始使用。会话数据保存于本地 data/ 目录（已被 .gitignore 忽略，不会随版本提交）。

## 3. 大模型 API 配置

所有模型配置在应用内「设置 → 模型」页完成，保存后写入本地 SQLite 数据库。

### 3.1 必填项与模型分组

Delepi 通过 OpenAI 兼容 API 对接大模型服务，模型配置分为三组：

| 模型分组 | 配置项 | 要求 |
| --- | --- | --- |
| 主智能体模型 | Base URL / API Key / 模型名称 | 必填（配置就绪检查仅校验本组三项与 Python 环境） |
| 执行子智能体模型 | Base URL / API Key / 模型名称 | 用于委派任务执行，需单独配置 |
| 视觉模型 | Base URL / API Key / 模型名称 | 仅图片分析场景需要（见 3.2） |

注意：API Key 以明文存储在本地数据库中，请勿在共享或公开环境中泄露。

### 3.2 图片分析配置（多模态 + 视觉识别双开）

需要让模型理解上传图片、或使用图片识别工具分析本地图片时，须同时满足以下三项：

1. 开启「支持多模态协议」（主智能体多模态，默认开启）；
2. 开启「启用视觉识别」总开关（默认开启）；
3. 填写视觉模型 Base URL / API Key / 模型名称（图片识别工具在运行时直读该组配置）。

不进行图片分析时，无需配置视觉模型。视觉 / 多模态模型示例（仅为示例列举，不构成支持范围清单）：Qwen3.5～Qwen3.8 系列、Kimi K3、MiniMax M3 等。

### 3.3 视觉识别开关联动说明

- 视觉识别默认开启。开启时会提示「开启视觉识别需配置模型 API，否则图片识别会报错」；视觉模型三项未配置时，开关旁同步显示未配置警示。
- 关闭视觉识别后：
  - 视觉模型三个输入框（Base URL / API Key / 模型名称）禁用，已填写的值保留；
  - 「支持多模态协议」开关同步禁用并提示暂不生效——多模态实际生效条件为「视觉识别开启且多模态协议开启」，即关闭视觉识别后多模态能力随之关闭；
  - 图片识别工具双层禁用（工具声明层移除 + 执行层拦截），委派任务无法再调用该工具。

### 3.4 思考程度

执行子智能体提供三档思考程度：低（更快响应）、高（均衡推理）、最大（深度推理）。默认档位为「最大」。

## 4. 能做什么：应用场景与优势

先讲清楚这套东西最核心的一点：你不需要懂任何配置。你把需求说清楚——"帮我看看这个报错是怎么回事""把这份合同的条款梳理一下""给这组财报数据核对一遍再画张趋势图"——主智能体会自动判断该做什么（自动选任务类型）、该用什么方法（自动配技能标签），然后通过委派工具把任务交给执行子智能体，一步步执行、一轮轮闭环，直到把你的需求办完。整个过程你只管提需求、看结果，不用手动配任务、配技能、配类型。

为什么能做到"全自动"？因为主智能体不是靠猜：它要委派任务，就必须把任务名称、任务类型、任务目标、规则约束、交付物类型、交付物描述、任务上下文、技能标签这 8 个字段全部填清楚（缺一不可）；选任务类型要符合内置触发规则；配技能要按技能标签对应的工作流模板来。所以下面两节，就是这套"自动判断"背后的两本字典：任务类型管"做什么"，技能标签管"怎么做"。

### 4.1 任务类型：做什么

任务类型一共有 8 种，主智能体根据你的需求自动选择，每种都有明确的触发规则和交付类型限制：

- **信息整理**：材料比较杂、事实比较散时，先把关键特征、结论和证据链汇总核实，交付**权威结论**。
- **诊断问题**：遇到报错、异常、差异、瓶颈、错误结果、状态不一致这类问题，分析实际根因，交付**权威结论**。
- **研究探索**：需要交叉分析、深挖显式/隐式/细微线索时使用，交付**线索集合**或**关键材料**。
- **设计方案**：目标对象还缺核心设计、没法直接落地时使用，交付**方案**。
- **统筹规划**：后续任务复杂度高、需要先明确整体规划时使用，交付**详细规划**。
- **执行落地**：事实和结论都齐了、要真正动手产出东西时使用，交付类型按实际产物确定（改好的文件、生成的图表、写完的文档都算）。
- **编写用例**：需求里包含"写测试用例"，或者最终交付物缺验证手段时使用，交付**测试用例**或**文件链接**。
- **验收验证**：需要执行测试用例、对最终交付物做回归验证时使用，交付**权威结论**。

可以这样理解：任务类型就是"这一轮要干的事"，复杂的需求会被自动拆成多轮任务，按触发规则一件件委派，直到目标达成。

### 4.2 技能标签：怎么做

任务类型决定"做什么"，技能标签决定"怎么做"。技能标签一共 8 种，每一种都对应 skills 目录下的一套专业工作流模板——选了这个技能，执行子智能体就会按这套模板一步步走，而不是自由发挥：

- **问题诊断**（issue-location）：报错、异常、差异、瓶颈、错误结果、状态不一致等问题追踪和根因定位。
- **方案设计**（solution-design）：方案、结构、接口、流程、数据、权限、交互和执行路径设计。
- **自动化交互**（simulation-operation）：在授权范围内执行真实请求、浏览器、远程命令、界面交互、文件链路或截图识别，并取得可核验证据。
- **用例编写**（use-case-writing）：按需求、变更、接口、流程、风险或验收口径设计可执行测试用例。
- **用例执行**（use-case-execution）：按既有测试用例执行网站、API、单元和应用程序测试，记录执行过程、阻塞和结果。
- **执行变更**（change-execution）：新增、修改、修复、重构、优化等会改变既有或新增产物的任务。
- **调查研究**（research-analysis）：基于已知或可取得材料建立证据链，判断研究对象之间的事实关系、比较关系和结论成立性。
- **视觉设计**（visual-design）：海报、封面、插画、图标、示意图、视觉素材等视觉内容的设计和生成。

技能标签由主智能体自动绑定，一个任务绑定 1 到 3 个技能，多了反而不聚焦。原则上任何任务类型都可以使用任何技能标签，但有几条内置的限制值得知道：任务类型为【验收验证】时禁止使用【用例编写】技能（必须先有适配的用例才能做验收验证）；任务类型为【研究探索】时禁止使用【问题诊断】技能；任务类型为【诊断问题】则必须使用【问题诊断】技能。这些限制写死在提示词里，保证"做什么"和"怎么做"始终匹配。

### 4.3 典型应用场景

下面用几个具体场景，把"智能体自动怎么干"和"相比传统方式优势在哪"讲透。

**软件开发场景**

- **改 BUG**：把报错信息、日志、复现步骤丢给它（也可以附带截图）→ 主智能体先触发【信息整理】汇总关键事实 → 再触发【诊断问题】并绑定【问题诊断】技能定位根因 → 确认后触发【执行落地】绑定【执行变更】技能实施修复 → 需要回归时，追加【编写用例】（绑定【用例编写】技能）和【验收验证】（绑定【用例执行】技能）做完整闭环。传统做法是人先读日志猜原因、再手改代码、再手写回归用例，每一步都要人盯着；这里全程由主智能体编排，你只需要在关键节点确认方向。
- **做项目**：描述项目目标、约束与现有材料 →【信息整理】收集核实事实 →【设计方案】绑定【方案设计】技能产出核心方案 →【统筹规划】产出详细执行规划 →【执行落地】按规划实施。传统做法要自己梳理需求、画方案、排计划、盯执行；这里方案和规划由专业模板保证质量，你只负责说清楚要什么。
- **自动化测试**：提供需求、变更说明或被测对象 →【编写用例】绑定【用例编写】技能生成可执行测试用例 →【验收验证】绑定【用例执行】技能逐条执行并输出执行报告与缺陷清单 → 涉及真实界面交互与截图取证时，由【自动化交互】技能在 Python 运行时安装并使用浏览器自动化库，按用例驱动页面操作，以截图与识别结果核验界面状态。相比手工点点点，这套流程把"写用例—跑用例—取证"串成了自动闭环。

**法律与合规场景**

- 合同条款梳理与风险审查：把合同文档（Word/PDF）作为资料文件提供 →【信息整理】提取条款与关键事实 →【诊断问题】定位风险点（比如违约责任、争议解决、保密义务等条款的缺失或表述不清）→【设计方案】给出修改方案 →【执行落地】产出修改版本文档 →【验收验证】输出审查报告。要说明的是：这套能力基于内置 Python 的 Word/PDF 读写与文本处理能力，处理的是你提供的资料文件本身，不会自动联网检索外部法律数据库。它的价值在于——条款梳理、风险点定位、修改建议、审查报告都按专业工作流模板产出，每一步有据可查，不会漏项。

**财务报表场景**

- 读财报、核对数据、生成图表：上传财报 PDF 或 Excel 文件 →【信息整理】梳理关键财务数据 →【执行落地】用内置 Python 的 openpyxl / pandas / pdfplumber 读取并核对数据，用 matplotlib 生成趋势图、占比图等图表 →【验收验证】核对数据与图表的准确性后交付。相比手动开 Excel 逐格核对、再手工画图，这里从"读文件—核数据—出图表—验结果"整条链路自动完成，图表和数字都经过校验，不容易出现"数据抄错、图表对不上"这类问题。

**研究分析场景**

- 资料整理 → 线索深挖 → 交叉验证 → 结论报告：把研究资料（文档、报表、数据文件）交给它 →【信息整理】汇总事实与证据 →【研究探索】绑定【调查研究】技能，基于材料建立证据链、交叉验证各对象之间的事实关系 → 再委派【信息整理】把线索提炼成结论 → 输出结论报告。相比自己翻资料、做笔记、反复核对，这套流程把"整理—深挖—验证—成文"按模板串起来，线索不丢、结论有依据。

### 4.4 为什么适合这些场景

回头看这些场景，它们有几个共同点：目标明确（改好 BUG、出份审查报告、核对完数据）、材料可提供（日志、合同文件、财报、研究资料）、产出可验证（修复结果、报告、图表都能被检查）。这恰好是 Delepi 最擅长的地方：

- **自动委派，不用人盯流程**：主智能体按触发规则自动决定先做什么、后做什么，每一轮委派完自动判断下一步，你不需要在中间当"监工"。
- **自动配置，不用人配参数**：任务类型、技能标签、交付类型全部自动选择，你永远不需要手动去配"这个任务该用哪个类型、绑哪个技能"。
- **多轮闭环，边做边验**：复杂需求拆成多轮任务，每轮结果回到主智能体继续推进，过程中随时可验证、可调整。
- **验收兜底，保证准确交付**：重要交付物都会走【编写用例】+【验收验证】闭环，交付前先被用例检验过，避免"看起来做完了、实际经不起检查"。

一句话总结：这套机制把"判断、分工、执行、验证"都自动化了，你要做的就是描述清楚需求，然后验收结果。

## 5. 执行能力与工具

上一章讲了"派活"的逻辑，这一章说说"干活"的家伙什——执行子智能体真正动手时，靠的是三把工具和一套内置 Python 环境。

**三大执行工具**

- **run_exe（命令行执行）**：执行非交互、多行脚本，适合跑命令、批处理这类操作。单段脚本不超过 8000 字符，默认 180 秒超时，输出超限自动截断，统一按 UTF-8 处理，并且会拒绝挂起、常驻类风险命令——既给足了能力，也防住了"卡死"。
- **run_with_python（Python 脚本执行）**：写 Python 代码执行。脚本会先落盘、经过 py_compile 预校验通过后才真正执行，默认 180 秒超时，同样统一 UTF-8。适合复杂逻辑、批处理、文件改写这类活。
- **inspect_image（图片识别）**：识别本地图片中的可见事实——文字、数字、界面元素、表格结构、异常细节等。它运行时直读视觉模型配置，需要"视觉识别开启"（视觉识别总开关与主模型多模态双开）才可用；不做图片分析时，不需要配置视觉模型，工具会自动降级为前两个。

**内置 Python 环境**

执行子智能体自带一套 Python 3.14.6 环境（首次启动自动下载初始化），并预置 14 个第三方包，覆盖能力相当广：

- 文档读写：Word（python-docx）、Excel（openpyxl、xlsxwriter）、PPT（python-pptx）、PDF（pdfplumber、PyPDF2）；
- 网络与远程：HTTP 请求（requests、httpx）、SSH 连接（paramiko）；
- 图像处理：pillow；
- 数据与可视化：pandas、numpy、matplotlib、networkx（数据报表、图表、组织架构图绘制）；
- TCP / UDP 通信由 Python 标准库 socket 支持。

依赖安装级别可选：核心 6 包 / 推荐 14 包（默认）/ 完整 24 包，支持配置 pip 镜像源。预置清单之外的依赖（比如浏览器自动化库）可以在任务执行过程中联网安装，装完即可使用。

把这一章和上一章的场景对照起来看就很清楚：处理法律文档靠 python-docx / pdfplumber 读 Word 和 PDF；核对财务报表靠 openpyxl / pandas 读写 Excel、matplotlib 画图；做研究分析靠文档解析、数据整理加图表输出；自动化测试靠浏览器自动化扩展加截图识别。工具是"手"，技能模板是"流程"，两套配合，前面说的那些场景才真正落地。

## 6. 提示词工程特点

这套系统"听话、不偷懒、不乱来"，秘密藏在提示词工程里。这一章讲三个关键设计。

**全中文提示词体系**：系统提示词、技能模板、工具描述全部用中文编写，直接面向中文任务语境。你在中文环境里提需求，模型理解需求、拆任务、写约束的整个链条都是中文的，不存在"中文需求翻译成英文再理解"的信息损耗。

**流程图即约束**：主智能体的标准逻辑流程图（Mermaid 图）是内嵌在提示词里的一部分，而不是给人看的示意图。模型必须按流程图从开始到结束、按节点顺序推进；跳过、重排、合并流程节点，都被明确定义为致命错误。换句话说，模型"先想再做、每步必走"不是靠自觉，而是写进提示词的硬约束。

**强制输出约束（可以叫它"图钉原理"）**：每个技能模板的末尾都有一大段"必须输出"要求——流程节点链路、核验证据链、迭代过程、风险点等等，把关键流程节点的完成情况与输出义务绑在一起。这就像拿图钉把关键环节钉死在桌面上：模型想交差，就必须先把这些环节走完并写出来，想跳过关键步骤"蒙混过关"根本交不出合格结果。这是这套系统"执行不偷懒"的关键设计——输出义务就是检查点，走没走过，一看输出就知道。

## 7. 上下文压缩能力

长会话聊到后面，上下文会越来越大，模型记不住、也容易超限。Delepi 靠"上下文压缩"解决这个问题。

**什么时候触发**：未压缩上下文超过 64K（65536）字符阈值时自动触发；如果多模态开启且当轮输入包含图片，则强制触发——图片占的上下文很大，必须及时压缩。

**压缩成什么**：调用主模型把历史消息总结成一份固定五章节的结构化摘要——事实和结论清单、线索清单、用户输入信息中的特征清单（含时序）、用户历史意图（含时序）、历史对话概要（含时序）。五个章节都带时序，保证"哪轮说的、什么时候发生的"不丢失。

**存到哪里**：压缩结果写入本地 SQLite 的 context_compressions 表；写入失败会自动重试，至多 3 次、每次间隔 10 秒，尽量避免压缩成果丢失。

**怎么用**：压缩完成后的后续轮次，用"背景信息 + 消息边界说明"的方式承接历史，而不是把几千行历史原样塞回去——既保留了关键信息，又把上下文规模控制住。

效果就是：长会话里关键的事实、结论、线索、意图不会随着轮次增加而丢失；上下文规模长期可控，不会越聊越臃肿；哪怕会话中断或重启，也能从压缩记录里把历史承接起来，接着聊。

## 8. 适配与不适配场景

Delepi 以「准确度优先」为性能取向，对应代价是流程较长：

- **适配场景（准确度优先的多步复杂任务）**：缺陷修复与根因诊断、项目方案与统筹规划、自动化测试与网页自动化、文档批量处理等。此类任务通过多轮委派、强制输出约束与验收闭环换取更高的完成准确度。
- **主要代价**：需求理解、任务委派、工具执行、结果回传与再决策构成多轮循环，整体耗时高于单轮直答，不追求极致响应速度。
- **不适配场景**：追求秒级即时响应的轻量问答、简单单步查询或单条文本改写等任务；此类任务的流程开销大于收益，建议直接使用普通对话工具。
