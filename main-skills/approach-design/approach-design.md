
### 思路设计逻辑流程图（**必须严格按照顺序执行，逐个节点执行，从开始到结束**）
```mermaid
flowchart TD
  START[开始] --> A[输入【用户最新意图】和当前所有已知事实]
  A --> B[分析该场景牵涉的【实体】及其【实体类型】，理清彼此之间的关联结构]
  B --> C[理清【用户最新意图】中【非开放意图】和【开放意图】]
  C --> D[将【开放意图】视作【创新需求】，同时一律排除【用户最新意图】中没有的所有【假设】和所有【预设条件】]
  D --> E{判断【用户最新意图】是否需要【工程化或者体系化】交付}
  E -- 是 --> Y[发起【设计方案】任务]
  E -- 否 --> F{判断当前【关键设计要素】是否充足}
  F -- 是 --> G{判断是否需要获取【最新、最权威】的知识}
  F -- 否 --> H[标记需要获取更多的【关键设计要素】]
  G -- 是 --> I[标记需要获取更多【最新、最权威】的知识]
  G -- 否 --> J[依据【目标问题】，标记需要尽可能获取【最权威、最新、最简洁】的【常规思路】]
  H --> J
  I --> J
  J --> K[标记需要获取当前【常规思路】是否可解决目标问题的【结论】]
  K --> L[依据当前所有已知事实和所有标记，同时按照【思路研究规则】，发起【研究探索】任务]
  L --> M{判断当前是否存在任何一条【常规思路】具备完美解决【目标问题】的所有条件}
  M -- 是 --> N[输出所有符合的【常规思路】，并将【最权威、最简洁、最有效】的【常规思路】列为【推荐】]
  M -- 否 --> O[根据当前所有已知事实和所有【常规思路】，穷举发散出更多【非常规思路】，形成【非常规思路集合】]
  N --> END[结束]
  O --> P[依据当前已知事实，排除有【直接证据】证明不具备【可行性】的【非常规思路】，更新【非常规思路集合】]
  P --> Q[排除无法完整解决【目标问题】的【非常规思路】，更新【非常规思路集合】]
  Q --> R[排除无法【逻辑自洽】的【非常规思路】，更新【非常规思路集合】]
  R --> S{判断【非常规思路集合】数量是否为0}
  S -- 是 --> T{判断当前【非常规思路】是否已穷举尽}
  S -- 否 --> V[发起【研究探索】任务，按照【思路研究规则】对【非常规思路集合】展开研究]
  T -- 是 --> U[输出无法解决【目标问题】并说明原因]
  T -- 否 --> O
  U --> END
  V --> W{判断是否存在一条【非常规思路】具备可行性}
  W -- 是 --> X[将当前【非常常规思路】视作【创新思路】并输出]
  W -- 否 --> T
  X --> END
  Y --> Z[解读当前方案，从【专业领域】角度，理解方案成果和其中的核心思路]
  Z --> END
```
### 关键定义和解释(**必须严格遵守**)
 1. 【目标问题】：【目标问题】指诉求、边界与验收口径均已写明、仅解决路径待定的课题本体。
 2. 【实体】与【实体类型】：【实体】指【目标问题】范围内可以单独指称、可以单独追问的对象；【实体类型】指该对象归属的类别；【关联结构】指实体之间、实体类型之间存在的连接、层级与依赖关系，三者共同决定一条路径改动后会牵动哪些对象。
 3. 【工程化或者体系化】：【用户最新意图】存在工程化建设或体系化建设的含义；或者存在多个【设计需求】；或者还未设计【核心概念或体现架构】就需要交付成果；**若【用户最新意图】为纯研究讨论，则可自主视情况而定**。
 4. 【关键设计要素】：至少包含以下几类：
    - a.【目标问题】涉及的对象和关系结构；
    - b. 每个专业名词或专业术语的定义和解释；
    - c. 权威材料（如：技术、规范、标准、兼容性等）；
    - d. 【目标问题】涉及的所有【常规场景】和【非常规场景】。
 5. 【思路研究规则】：至少包含以下规则：
    - a. 对所有已知思路可行性研究并获取【可行性结论】。
    - b. 具备【可行性】的思路必须互相交叉对比【优缺点】。
    - c. 必须分析每个思路能够解决哪些问题，解决了哪些【痛点和难点】。
